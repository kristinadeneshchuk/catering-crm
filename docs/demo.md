# Демо NutriX на ~280 раціонів/день

Окрема демо-база для показу CRM потенційним клієнтам у масштабі середньої
кухні: ~280 доставок у будній день, ~120 у суботу, ~80 у неділю. Структура —
пропорційна реальним клієнтам (агрегати прода в `docs/demo-proportions.md`),
усі люди, телефони й адреси вигадані.

Відео-база `nutrix_demo` (для зйомки) — окрема, цей скрипт її не чіпає.

## Перебудова з нуля

```bash
scripts/nutrix-demo-280.sh
```

Скрипт:
1. перестворює базу `nutrix_demo_280`;
2. заливає `database/demo/nutrix_base.sql.gz` — схему й довідники (страви,
   техкарти, тарифи, цикл меню, вигадані постачальники) без клієнтів;
3. накатує нові міграції (`php artisan migrate`);
4. запускає `NutrixDemo280Seeder`.

Дати рахуються від **сьогодні**: історія ~90 днів, замовлення наперед ~16 днів,
маршрути/табель/склад — за останні 30 днів плюс вечір сьогодні й ранок завтра.
Щоб демо не старіло — перед показом просто перезапустити скрипт (≈15–20 хв).
Генератор детермінований (фіксоване зерно), тож у той самий день результат однаковий.

## Запуск

Потрібен `.env.nutrix280` у корені (не в git): копія `.env.nutrix` з
`DB_DATABASE=nutrix_demo_280`, `APP_URL=http://localhost:8093`, `MAIL_MAILER=log`
і порожніми Telegram-токенами. Логін `demo@nutrix.test` (адмін),
менеджери `manager@…`, `manager1@…` … `manager5@nutrix.test`, кухня `cook@nutrix.test`;
пароль — змінна `NUTRIX_DEMO_PASSWORD` з env.

```bash
cd public && APP_ENV=nutrix280 PHP_CLI_SERVER_WORKERS=4 php -d memory_limit=1024M -d max_execution_time=120 -S 127.0.0.1:8093 ../vendor/laravel/framework/src/Illuminate/Foundation/resources/server.php
```

Це те саме, що `php artisan serve`, але з 1 ГБ памʼяті: аналітика за місяць на такому
обсязі бере ~210 МБ, а стандартні 128 МБ дають 500.

або пункт `nutrix-demo-280` у `.claude/launch.json`.

## Що всередині

- ~2580 клієнтів (≈1380 з історією за 90 днів + 1200 давніх), ~7300 замовлень, ~45 тис. днів доставки; бренди FitDay / Green Box / Smart Food (56/40/4%).
- Замовлення й дні створюються моделями: ціни з тарифів, статуси — `recomputeStatus()`,
  `paused` ставиться руками й лишається (sticky), нарахування/оплати — транзакціями.
- Ритм як у проді: більшість замовлень пн–пт, частина щодня; ранок/вечір 50/50,
  індивідуальні ~29% днів (частина — з персональним меню), сімейні дочірні ~5%.
- Виключення продуктів у ~48% клієнтів, заміни (`order_replacements`) — через
  сервіс замін на першому замовленні, далі успадковуються продовженнями.
- Логістика: план «приходить» від RouteLogix (HTTP підроблено в сідері) і пишеться
  `RouteLogixService` — номери маршрутів на наліпках, виїзди, ставки курʼєрів у табелі.
  ~13 маршрутів на зміну по ~11 точок, 30 курʼєрів.
- Склад: щоденні приходи під план кухні (із запасом) і списання за нормою
  `KitchenStockDebit`; свіжа ШІ-чернетка накладної на сьогодні.
- Каса: оплати клієнтів (картка/готівка/ФОП), ЗП щопонеділка, закупівля, оренда,
  комуналка, реклама, генератор.
- Дзвінки утримання, оцінки страв, сповіщення кухні, бонуси/штрафи.

Під час сідування всі зовнішні HTTP-запити заблоковано (`Http::preventStrayRequests()`).

## Відомі особливості

- Вихідні нижчі за будні (сб ~90, нд ~60) — так само, як у проді: більшість замовлень пн–пт.
- Майбутні 14 днів заповнені «наперед оформленими» продовженнями, тож активних замовлень
  більше, ніж у реальному житті в будь-який момент, а в останні дні каса показує більше оформлень.
- Найповільніші екрани на такому обсязі: «Управлінська аналітика» ~3,5 с за поточний місяць
  і ~12 с за повний місяць, фасувальний лист ~4 с, план виробництва / закупівля / наліпки 2–3 с.
  Решта — до 1,5 с.
- Сховані в коді сторінки (план кухні, чати, ШІ-агенти, банк, звірка) дають 403 — їх немає в меню.
- Перевірка всіх сторінок: `node _local/nutrix-demo-280/crawl.cjs urls3.txt [email]` (локальні скрипти, не в git).
