# Підтвердження оплат і виплати курʼєрам

ТЗ погоджене власником 11.09.2026, зроблено 12.09.2026.

## Етап 1. Оплату підтверджує тільки менеджер

Будь-яке «гроші є» — від клієнта, агента, курʼєра чи виставленого рахунку —
стає **заявою** (`payment_claims`). Заява ніколи не змінює `is_paid`. Гроші
зʼявляються, лише коли менеджер натисне «Підтвердити» і вибере касу.

- **Система → Чекають підтвердження** — список заяв. Фільтри: бренд, джерело,
  курʼєр, дата, «лише розбіжності». Пара «клієнт + курʼєр» про ту саму готівку
  показана одним рядком, різні суми — червоним.
- Доступ: `admin` і `manager`.
- Кнопка «Оплачено» в картці чату — той самий сценарій, з вибором каси.
- Запобіжник у `Transaction::creating`: надходження на замовлення без каси не
  проходить, роль без права на касу отримує відмову. Діє для всіх пʼяти шляхів,
  якими в CRM потрапляють гроші клієнта.

API агента — у [inbox-api.md](inbox-api.md), розділи 11 і 12.

## Етап 2. Виплата курʼєру з погодженням у Telegram

1. **Підключення курʼєра.** Співробітники → іконка 🔗 у рядку курʼєра → посилання.
   Курʼєр відкриває його в Telegram і тисне «Start». Посилання одноразове.
2. **Шаблон звіту.** Бот сам надсилає заповнений шаблон на початку зміни
   (05:45 ранок, 17:00 вечір) і нагадує в кінці (12:30, 22:00) тим, хто не здав.
   Курʼєр дописує фініш і готівку та шле назад одним повідомленням із двома
   фото одометра. «+» — узяв рівно очікувану суму, порожньо — не брав.
3. **Прийом.** Пробіг іде через той самий сервіс, що й сторінка Логістики
   (баланс рухається на різницю компенсації). Готівка стає заявою
   `courier_cash` і потрапляє в «Чекають підтвердження».
4. **Погодження.** Коли здано всі зміни дня, власник і старший менеджер
   отримують розклад виплати з кнопками ✅ / ✏️ / ❌. Реагуємо лише на їхні
   Telegram-ID. ✏️ веде в **Система → Виплати курʼєрам**; після правки
   повідомлення в обох чатах оновлюється.
5. **Виплата.** Погоджена сума видна в «Зарплатах» під боргом курʼєра. Платять,
   як і раніше, вручну; кнопка «Виплатити» закриває погоджені дні періоду.

Логіку нарахування `employees.balance` етап 2 не чіпає — лише додає звіт і
погодження поверх неї. Розклад у Telegram дорівнює рівно тому, що за день
рахують «Зарплати»; якщо ставка в Табелі відрізняється від розрахункової,
різниця показана окремим рядком «Коригування в Табелі».

## Запуск на проді

Порядок — після ОК власника на міграції.

```bash
# 1. .env на horenko
TELEGRAM_BOT_WEBHOOK_SECRET=<bin2hex(random_bytes(24))>
TELEGRAM_BOT_USERNAME=<імʼя бота без @>

# 2. після деплою
php artisan config:clear
php artisan telegram:bot-webhook          # підключити вебхук
php artisan telegram:bot-webhook --info   # перевірити
```

Час розсилок змінюється змінними `COURIER_REPORT_MORNING_AT`,
`COURIER_REPORT_MORNING_REMIND_AT`, `COURIER_REPORT_EVENING_AT`,
`COURIER_REPORT_EVENING_REMIND_AT`.

## Чого поки немає

- **Способу оплати в картці замовлення.** Поле `orders.payment_method` є і
  заповнюється з API агента, але в форму замовлення його не додано:
  `OrderResource.php` зараз містить незакомічений редизайн. Без нього в шаблон
  курʼєра потрапляють лише замовлення, де клієнт сказав агенту «передам
  готівкою», і ті, що оформлені через API з `payment_method: cash`.
- **Mini App** замість текстового шаблону — ТЗ відкладає на потім.
