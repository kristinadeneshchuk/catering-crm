# ТЗ: ШІ-агенти всередині CRM — «Меню» і «Переписки»

Статус: v1 від 24.10.2026, чернетка на погодження власника. Розвиває «Пульт ШІ-агентів» (`docs/ai-agents-api.md`), нічого з нього не викидає.

**Мета.** Роботу, яку зараз роблять дві чат-сесії Claude на Маку власника («Індивідуальні раціони» та «Inbox задачі»), переносимо на сервер CRM. Менеджер ставить задачу агенту прямо з картки клієнта чи замовлення, бачить хід роботи й погоджує результат. Мак і чати для цього більше не потрібні.

**Принцип лишається той самий.** Агент у бойові дані не пише. Він кладе пропозицію, код її перевіряє, людина погоджує, і лише тоді CRM виконує (`ProposalDesk`).

## 1. Ролі

| Хто | Що робить |
|---|---|
| **Агент «Меню»** (`menu`) | Складає меню на період і заміни. Подає `individual_week_menu` / `order_replacements`. Сам ні з ким не листується |
| **Агент «Переписки»** (`chats`) | Читає чати клієнтів в Inbox. З нових повідомлень робить пропозиції (§5). На запит перевіряє пропозиції «Меню» проти чату (§6). Готує `client_message`. Клієнтам **сам не пише ніколи** |
| **Менеджер** | Ставить задачі з картки, відповідає на питання агента, погоджує прості типи (виключення, контакти, перенос дня — за списком `AI_MANAGER_TYPES`) |
| **Власник** | Погоджує меню, повідомлення клієнтам, усе, що стосується грошей. Бачить витрати на ШІ й тижневий звіт |
| **Код (валідатори)** | Перевіряє кожну пропозицію до того, як її побачить людина (§4). Жорстка помилка повертається агенту, до людини така пропозиція не доходить |

## 2. Де і як працюють агенти

**Рішення: усередині CRM, на сервері horenko (88.99.169.99), як черговані Laravel-задачі.** Окремого сервісу немає. Причини:
- дані, сервіси (`DishCatalog`, `IndividualWeekMenu`, `ProposalDesk`) і ключ Anthropic уже тут (`OpsAi`, SDK `anthropic-ai/sdk`);
- воркер `horenko-worker` під supervisor уже працює, деплой той самий (push у main);
- агенту не потрібні ні shell, ні файлова система, лише інструменти CRM. Тому Agent SDK (Claude Code як бібліотека) і Managed Agents тут зайві.

**Механіка.**
- Окрема черга `agents` і окрема програма supervisor `horenko-agents` (1–2 процеси, таймаут 20 хв). Так довга задача не блокує накладні й Telegram.
- `RunAgentTask` job бере задачу і крутить цикл tool use через PHP SDK: модель → виклик інструменту → результат → далі. Кожен крок пишеться в тред задачі (§3.2).
- Інструменти — це **PHP-методи всередині CRM** з тими самими межами, що в API `agents/v1`: читання плюс подати пропозицію, повідомлення, пам'ять. HTTP-виклики самих себе не робимо.
- Моделі: «Меню» — `claude-opus-5-5`, effort `high`. «Переписки»: сортування нових повідомлень — `claude-sonnet-5-5`, effort `low`; пропозиції й перехресна перевірка — `claude-sonnet-5-5`, effort `medium`. Змінюється в `.env` (`AGENT_MENU_MODEL`, `AGENT_CHATS_MODEL`).
- Prompt caching: незмінну частину (правила, опис інструментів, довідник груп продуктів) ставимо першою з `cache_control`.
- Обмеження: `AGENTS_DAILY_CAP_USD` (окремо від `ANTHROPIC_DAILY_CAP_USD` операційного ШІ), ліміт кроків на задачу (40), ліміт токенів на задачу. Коли ліміт вичерпано, задача отримує статус `failed` з причиною, власник дістає сповіщення.
- Облік: кожен виклик моделі пишеться в `ai_runs` (purpose `agent_menu` / `agent_chats`, токени, $). Сума видна в задачі.
- Версія SDK 0.49: перевірити, чи є `toolRunner()`. Якщо немає — ручний цикл (≈80 рядків), оновлювати SDK не обов'язково.

**Перехідний період.** API `agents/v1` для сесій на Маку лишається. Серверний агент отримує новий slug, і щоб двоє не робили одне й те саме, вводимо **блокування «клієнт × період»**: поки задача в роботі, друга пропозиція на ті самі дати отримує 422 від будь-кого.

## 3. Екрани для менеджера (Filament)

### 3.1 «ШІ → Задачі» (новий список)
Колонки: №, агент, клієнт / замовлення, що зробити (коротко), період, статус (`new` / `in_progress` / `waiting_human` / `done` / `failed` / `cancelled`), хто поставив, дедлайн, $ витрат, к-сть пропозицій.
Фільтри: мої, чекають на мене, агент, клієнт. Для кожного менеджера лічильник «Чекає на вас N».

### 3.2 Сторінка задачі = тред
- Угорі: клієнт, замовлення, період, текст задачі, статус, кнопки «Скасувати» та «Перезапустити».
- Стрічка ходу роботи, коротко людською мовою: «Читаю переписку за 14 днів», «Знайшов 3 нові виключення: горох, батат, свинина», «Перевірка: обід 28.10 — кукурудзяний крохмаль у ПФ «Соус…», замінюю страву». Технічні виклики згорнуті під «деталі».
- Питання агента до менеджера (статус `waiting_human`) і поле відповіді. Відповідь одразу будить агента.
- Пропозиції задачі — картки з бейджами перевірок (§4) і кнопками **Погодити / Правки (коментар) / Відхилити**. Правки повертаються агенту, і він подає нову версію в тому ж треді.

### 3.3 Кнопка «Доручити агенту»
На картці клієнта, на картці замовлення й у списку замовлень (масова дія). Модальне вікно з шаблонами:
- **Скласти меню на період** (Меню): замовлення, дати від–до, побажання текстом;
- **Заміни на період** (Меню);
- **Перевірити переписку** (Переписки): «за N днів / з дати», що шукати (виключення, скарги, все);
- **Вільна задача**: агент на вибір і текст.

Дедлайн підставляється сам: меню на D — до 10:00 D−1, меню на тиждень — до четверга.

### 3.4 Картка клієнта — блок «ШІ»
Активні задачі, останні пропозиції, «Конфлікт з перепискою» (§6), профіль харчування (§7.2).

### 3.5 Telegram
Як зараз: пропозиція з кнопками ✅/❌ погоджувачу. Нове: питання агента йде менеджеру, який поставив задачу (реплай = відповідь у тред).

## 4. Валідатори (код, не модель)

Запускаються на кожну пропозицію в момент подачі, по свіжих даних CRM. Результат зберігається в `ai_proposals.checks` і показується бейджами. **Жорстка** помилка = 422 агенту, людина таку пропозицію не бачить. **Попередження** пропозицію пропускає з жовтим бейджем; щоб попередження лишилось, агент має його пояснити.

| # | Перевірка | Рівень |
|---|---|---|
| V1 | **Виключення на всю глибину ПФ**: рекурсивно розкрити страву до сирих продуктів і звірити з виключеннями клієнта й замовлення. Діє і для другої людини в парі, і для **дублів картки**, якщо є зв'язок | жорстка |
| V2 | **Групи-синоніми**: «кукурудза» → зерно, крохмаль, «Овочі мексиканські»; «горох», «бобові», «гриби», «риба річкова / біла», «морепродукти», «молочне / лактоза». Нова таблиця `ingredient_groups` + `ingredient_group_items`, а не регекси (регекси вже хибили) | жорстка |
| V3 | **Дні**: дата є серед `order_days` замовлення, не пауза й не скасована | жорстка |
| V4 | **Битий продукт**: інгредієнт з 0 ккал (крім солі, води, спецій) або ккал ≠ 4Б+9Ж+4В більше ніж на 25 % | жорстка (список виправлень — власнику) |
| V5 | **КБЖВ дня проти цілі** замовлення (`calories`, `target_*_g`), рахується з техкарт CRM у момент подачі | > 10 % попередження, > 20 % жорстка |
| V6 | Собівартість дня ≤ 30 % ціни дня (є) | попередження |
| V7 | Повтори 28 днів і двічі в меню, з урахуванням `repeat_ok` (є) | попередження |
| V8 | Навантаження кухні: ≤ 6 страв поза циклом на день на всіх, бажано ≤ 4 окремих партій (є, розширити) | попередження |
| V9 | Правила профілю клієнта (§7.2): «паста раз на день», «курка не частіше…», «лише тваринний білок» | попередження |
| V10 | Дедлайн: меню на D після 10:00 D−1 | попередження + позначка «узгодити зі старшим зміни» |
| V11 | `client_message`: бренд і чат = бренд замовлення; без заготовок `[…]`; без згадок ШІ | жорстка |
| V12 | Нова страва без виходу чи з кг замість грамів (є) | жорстка |

Валідатори V1–V5 корисні й без агентів, тож їх **винести в окремий сервіс `MenuGuard`**. Пізніше на нього можна посадити генератор меню і `nutrition:menu:analyze`: зараз вони дивляться лише 2 рівні ПФ.

## 5. Агент «Переписки»: Inbox → CRM

### 5.1 Звідки читає (офіційний Agent API Inbox, `events-api.md`)
- **Webhook** `message.received` → `POST /api/agents/inbox-events` у CRM (HMAC `X-Inbox-Signature`, дедуп за `event_id`). На проді Inbox `AGENT_EVENTS_URL` порожній: вмикаємо **з ОК власника** (URL CRM + секрет у `/etc/inbox/inbox.env`).
- Резерв, якщо webhook мовчить: кожні 15 хв `GET /api/agent/conversations?updated_since=…`.
- Читання: `GET /api/agent/conversations/:id/messages`, `?crm_client_id=N`. Токен `AGENT_READ_TOKEN` лише в `.env` CRM.
- **Чатів у CRM не зберігаємо.** Тягнемо на час задачі, у пропозицію кладемо лише id повідомлення й цитату ≤ 200 символів як доказ.
- Від Inbox треба (задача для сесії Inbox): фото/голосові через агентський токен (зараз не віддає); розшифровки голосових у відповіді `/messages`.

### 5.2 Потік
1. Нові вхідні складаються пачкою по чату (вікно 10 хв) → Sonnet, effort low, сортує: `нічого` / `виключення` / `скарга` / `пауза-перенос` / `адреса-контакт` / `побажання до меню` / `питання без відповіді`.
2. Якщо є що робити → задача агенту «Переписки» з контекстом чату й картки → пропозиції.
3. Якщо в чаті немає `crm_client_id` або є дублі картки — пропозиції не робимо, а пишемо менеджеру: «чат X: привʼязати до клієнта» (кнопки з кандидатами).

### 5.3 Нові типи пропозицій (кожен = обробник у `ProposalDesk`)

| Тип | Payload | Після погодження |
|---|---|---|
| `client_exclusion_add` | client_id, ingredient_ids / group_id, людина в парі, цитата | `client_ingredient_exclusion` (+ дублі картки) і задача «Меню» перевірити вже складені дні |
| `client_profile_update` | stop / avoid / want_more / частоти / режим | профіль харчування (§7.2) |
| `order_day_change` | order_id, пауза / перенос / скасування, дати рівно як у чаті | `order_days`, потім звірка списку днів |
| `client_contact_update` | телефон / адреса / поверх / код / «де лишати» / час | картка клієнта |
| `client_complaint` | дата, страва, суть, фото-id | журнал скарг + сповіщення власнику (компенсації — лише власник) |
| `client_message` | (є) | відправка в Inbox після погодження |

Окремо, без пропозиції: «питання клієнта без відповіді > 2 год у робочий час» → нагадування менеджеру. Скарги висіли по 10–30 год.

## 6. Перехресна перевірка

1. **Код** — завжди (§4).
2. **«Переписки» перевіряє «Меню».** На кожну `individual_week_menu` автоматично ставиться підзадача: прочитати чат клієнта за 30 днів і звірити меню з усім, що клієнт казав («не їм», «більше білка», «не хочу рибу щодня», прохання з хвоста повідомлення). Результат пишеться в `ai_proposals.cross_check`: ✅ «суперечностей немає» або ⚠ «конфлікт з перепискою» з цитатою. Конфлікт — бейдж, а не блок: вирішує людина.
3. **«Меню» перевіряє «Переписки».** На `client_exclusion_add` агент меню перелічує вже погоджені дні з цим продуктом і подає `order_replacements` до них.
4. **Тижневий звіт власнику** (пн 09:00): задач / пропозицій / погоджено з першого разу / правки / жорсткі помилки валідаторів / конфлікти / $ витрат / що агент не зміг.

## 7. Знання: з теки на Маку → у CRM

### 7.1 Пам'ять агента (`ai_agent_memory`, ключі `rules:*`)
Із `STATUS.md` і `ПРАВИЛА_ПРОПИСУВАННЯ.md`: бренди окремо; спершу адаптувати цикл → пул клієнта → нова страва; ліміти кухні; дедлайни; «кухні — без грошей і без ШІ»; режими клієнтів. Сторінка «ШІ-агенти → Пам'ять» стає редагованою: власник править правила без програміста.

### 7.2 Профіль харчування клієнта (структуровано, не текст)
Зараз це `profiles/*.md`, `count_rules.py`, `client_memos.yaml`. Стане картою на клієнті:
- режим: `cycle_replacements` / `hybrid` / `own_menu_only` / `vip`;
- цілі КБЖВ (зараз `orders.target_*_g` часто NULL, а мають заповнюватися);
- stop / avoid / want_more (stop — у виключення, решта — у профіль);
- правила-частоти: «паста ≤1/день», «курка ≤N/тиждень», «білок лише тваринний»;
- пул улюблених страв (dish_ids);
- пам'ятка кухні: текст без грошей і без ШІ.

Перенесення робимо разовою командою `agents:import-rations` з dry-run, ~25 клієнтів. Власник переглядає diff, потім запис.

### 7.3 Що лишається за межами CRM
Сирі чати й голосові лишаються в Inbox, брифи на Маку — архів. Персональні дані до Anthropic ідуть так само, як уже йдуть в `OpsAi` (API без тренування на даних).

## 9. Вартість API (орієнтовно)

Ціни: Opus 5.5 — $4 / $20 за 1M токенів (вхід / вихід), Sonnet 5.5 — $2 / $10, читання кешу $0.20.

| Що | Розрахунок | $ |
|---|---|---|
| Меню на тиждень, 1 клієнт (Opus) | ~250k вхідних (70 % з кешу) + ~20k вихідних | ≈ $0.7–1.5 |
| 15 меню на тиждень + щоденні правки | | ≈ $15–30 / тиждень |
| Сортування чатів (Sonnet low) | ~150 пачок/день × ~6k токенів | ≈ $2 / день |

## 11. Порядок робіт

**Крок 1 — агент «Меню» на сервері + «Задачі ШІ» (~1 тиждень).** Окрема гілка `feat/ai-agents-server` від `feat/ai-agents`.
1. Міграції §8 (без `client_complaints` і `inbox_events`) — **ОК власника**.
2. `MenuGuard` (V1–V5, V9, V10) + групи-синоніми + тести.
3. `RunAgentTask` + інструменти «Меню» + черга `agents` + облік і стеля.
4. Екрани §3.1–3.4.
5. `agents:import-rations` (dry-run → ОК → запис).
6. **Тіньовий тиждень:** сесія на Маку працює як завжди, серверний агент складає меню паралельно для 3–5 клієнтів у режимі «лише показати». Порівнюємо. Після ОК власника перемикаємо.

Приймання: менеджер з картки ставить «склади меню X на 27–31.10». За ≤ 15 хв у CRM з'являється пропозиція з зеленими V1–V5. Після погодження меню в CRM, лист кухні правильний. Тести зелені.

**Крок 2 — агент «Переписки» (~1 тиждень).** Webhook Inbox (ОК власника на `inbox.env`) + сортування + типи §5.3 + привʼязка чатів. Тіньовий режим 3 дні: пропозиції бачить лише власник.

**Крок 3 — перехресна перевірка й звіт** (§6) — 2–3 дні.
