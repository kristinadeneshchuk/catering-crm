# Inbox API v1

Інтеграція CRM із зовнішньою системою листування (Telegram Inbox).

**Розподіл ролей.** Inbox веде переписку і показує менеджеру картку замовлення.
CRM зберігає бренди, тарифи, ціни, клієнтів і замовлення — і рахує суму.
Inbox ніколи не обчислює ціну самостійно: інакше дві системи розійдуться, і
клієнту назвуть одну цифру, а у звітах буде інша.

Каскад: **проєкт → тариф → діапазон калорій → дні → розрахунок → замовлення → рахунок**.

---

## Підключення

```
База:           https://crm.horenko-production.com/api/inbox/v1
Авторизація:    Authorization: Bearer <INBOX_API_TOKEN>
                Accept: application/json
```

Токен спільний для обох сторін, живе в `.env` CRM (`INBOX_API_TOKEN`).
Без нього — `401`. Якщо токен не заданий на боці CRM — `503`.

### Помилки

Усі відмови приходять як `422` у стандартному форматі Laravel, із людською
причиною українською:

```json
{
  "message": "Тариф «Від 1 дня» не має ціни для 2800 ккал (діапазон «Strong 2800»).",
  "errors": { "tariff_id": ["Тариф «Від 1 дня» не має ціни для 2800 ккал…"] }
}
```

Повідомлення можна показувати менеджеру як є.

## 1. Бренди

```http
GET /projects
```

```json
{
  "data": [
    { "id": 5, "code": "afood", "name": "afood", "active": true },
    { "id": 4, "code": "avocado_food", "name": "Avocado Food", "active": true },
    { "id": 2, "code": "u_fit", "name": "U-FIT", "active": true }
  ]
}
```

Кожен Telegram-акаунт в Inbox прив'язується до одного `id` назавжди — бренд
визначається акаунтом, менеджер його не обирає.

## 2. Каталог бренду

```http
GET /projects/{project_id}/catalog
```

```json
{
  "project": { "id": 5, "code": "afood", "name": "afood" },
  "tariffs": [
    {
      "id": 28,
      "name": "Від 1 дня",
      "min_days": null,
      "calorie_ranges": [
        { "id": 12, "label": "Lite 900-1000 ккал", "min_calories": 899,
          "max_calories": 1000, "price_per_day": 775 }
      ]
    }
  ]
}
```

**Показуємо лише те, що справді можна продати.** Тарифи без жодної ціни і
калорійності без ціни в каталог не потрапляють — обрати комбінацію, яка потім
впаде на розрахунку, неможливо.

`min_days` — мінімум днів за тарифом. `null` = обмеження немає. Не парсити
назву тарифу («Від 5-7 днів») — для цього і є поле.

## 3. Розрахунок вартості

```http
POST /quotes
```

```json
{
  "project_id": 5,
  "tariff_id": 28,
  "calories": 2400,
  "days": 5,
  "client_id": 845,
  "start_date": "2026-08-17",
  "discount": 200
}
```

`discount` — або число (разова знижка в гривнях), або
`{"type": "percent", "value": 10}`.

```json
{
  "project_id": 5,
  "tariff_id": 28,
  "tariff": { "id": 28, "name": "Від 1 дня" },
  "currency": "UAH",
  "calories": 2400,
  "calorie_range": { "id": 18, "name": "Strong 2400-2500 ккал",
                     "min_calories": 2399, "max_calories": 2500 },
  "days": 5,
  "price_per_day": 1170,
  "subtotal": 5850,
  "discount": 200,
  "delivery_price": 0,
  "total": 5650
}
```

**Ведучим є `calories` (число), а не `calorie_range_id`** — саме за числом CRM
знаходить діапазон, і це поле обов'язкове в замовленні.

**`quote_id` не повертається.** Розрахунок ніде не зберігається: при створенні
замовлення сума рахується наново тією самою формулою. Показуйте quote як
прев'ю, не як зафіксовану ціну.

`delivery_price` завжди `0` — доставка в суму замовлення не входить.

## 4. Пошук клієнта

```http
GET /clients/search?phone=0955532677
GET /clients/search?telegram_user_id=123456789
GET /clients/by-channel/telegram/{external_user_id}
```

```json
{
  "found": true,
  "client": {
    "id": 845,
    "full_name": "Міжно Аркадій Сергійович",
    "phone": "+38 (095) 553-26-77",
    "telegram_username": "arkadiy",
    "telegram_user_id": "123456789",
    "allergies": null,
    "exclusions": null,
    "target_kcal": 1600,
    "balance": -4490,
    "addresses": [
      { "id": 91, "address": "вул. Ахматової, 13Б", "entrance": "1",
        "apartment": "88", "floor": null,
        "delivery_comment": "Домофон: 258\nПередача: залишити у консьєржа",
        "is_default": true }
    ]
  }
}
```

Телефон шукається за цифрами, по останніх дев'яти — формат не має значення.
`0955532677` знайде клієнта, записаного як `+38 (095) 553-26-77`.

Не знайшли — `{"found": false, "client": null}`, теж `200`.

## 5. Створення або оновлення клієнта

```http
POST /clients
```

```json
{
  "project_id": 5,
  "full_name": "Міжно Аркадій Сергійович",
  "phone": "0955532677",
  "telegram_user_id": "123456789",
  "telegram_username": "arkadiy",
  "address": {
    "address": "вул. Ахматової, 13Б",
    "entrance": "1", "apartment": "88", "floor": null,
    "intercom": "258",
    "handoff": "Залишити у консьєржа"
  }
}
```

Спершу шукаємо наявного (за Telegram ID, потім за телефоном) — дубль не
створиться. Наявного не перезаписуємо порожнім, лише доповнюємо.

`intercom` і `handoff` окремих полів у CRM не мають — складаються в
структурований коментар до адреси, який бачить курʼєр.

Відповідь — той самий об'єкт, що в пошуку, зі статусом `201`.

## 6. Прив'язка каналу

```http
POST /clients/{client_id}/channels
```

```json
{ "channel_type": "telegram", "external_user_id": "123456789",
  "username": "arkadiy", "project_id": 5 }
```

На таблиці каналів стоїть UNIQUE `(channel, external_id)`: один Telegram-ID —
рівно один запис, незалежно від бренду.

## 7. Створення замовлення

```http
POST /orders
```

```json
{
  "project_id": 5,
  "client_id": 845,
  "tariff_id": 28,
  "calories": 2400,
  "days": 5,
  "start_date": "2026-08-17",
  "delivery_window": "morning",
  "discount": 200,
  "source": "telegram_inbox",
  "external_conversation_id": 158,
  "address": { "address": "вул. Ахматової, 13Б", "apartment": "88",
               "intercom": "258", "handoff": "Залишити у консьєржа" }
}
```

`delivery_days` (масив дат) — для «рваних» днів замість `days` підряд.

```json
{
  "order": {
    "id": 1499,
    "project": "afood",
    "status": "new",
    "payment_status": "unpaid",
    "is_paid": false,
    "client_id": 845,
    "client_balance": -5650,
    "calories": 2400,
    "days": 5,
    "start_date": "2026-08-17",
    "end_date": "2026-08-21",
    "price_per_day": 1170,
    "subtotal": 5850,
    "discount": 200,
    "total": 5650,
    "calorie_range": { "id": 18, "name": "Strong 2400-2500 ккал" }
  }
}
```

**`status` — рідний статус CRM** (`new` / `active` / `paused` / `finished`), він
відображає виробництво, а не оплату. Для оплати є окремі `payment_status` та
`is_paid`.

Разом із замовленням створюються дні доставки — без них воно не потрапляє ні у
виробництво, ні в логістику.

Якщо порахувати неможливо — `422`, і замовлення **не створюється взагалі**.

## 8. Історія замовлень клієнта

```http
GET /clients/{client_id}/orders
```

```json
{
  "client_id": 845,
  "client_balance": -5650,
  "data": [
    { "id": 1499, "project": "afood", "tariff": { "id": 28, "name": "Від 1 дня" },
      "calories": 2400, "days": 5,
      "start_date": "2026-08-17", "end_date": "2026-08-21",
      "status": "new", "payment_status": "unpaid", "is_paid": false,
      "subtotal": 5850, "discount": 200, "total": 5650 }
  ]
}
```

Останні 50, найновіші зверху. Звідси беруться «улюблений тариф», «останній
калораж» і кнопка повторити.

## 9. Рахунок на оплату

```http
POST /orders/{order_id}/invoice
```

```json
{
  "invoice": {
    "id": 519,
    "number": "1/1499",
    "date": "2026-08-13",
    "amount": 5650,
    "purpose": "оплата згідно рахунку №1/1499 від 13.08.2026 за доставку здорового харчування",
    "recipient_name": "ФОП Горенко Поліна Сергіївна",
    "iban": "UA703220010000026005340086870",
    "tax_id": "3748801687",
    "bank_name": "УНІВЕРСАЛ БАНК",
    "mfo": "322001",
    "pdf_url": "https://crm.horenko-production.com/invoices/<token>.pdf",
    "text": "Рахунок №1/1499 від 13.08.2026\nСума: 5 650.00 грн\n…"
  }
}
```

`text` — готовий до відправки блок із реквізитами, кожен окремим рядком: клієнти
платять з телефону і копіюють IBAN руками.

`pdf_url` — публічне посилання (без авторизації, захищене непередбачуваним
токеном). Його можна прикріпляти до повідомлення.

**Повторний виклик віддає наявний рахунок, а не новий номер** — у клієнта не
буде двох різних номерів на одне замовлення.

Реквізити копіюються в рахунок знімком: зміна ФОП чи банку не переписує
документи, які клієнти вже отримали.

Нумерація «порядковий/замовлення», окремо для кожного бренду.

Якщо у бренду не заповнені отримувач і IBAN — `422`.

## 10. Вебхук із CRM (зворотний бік)

Коли замовлення стає оплаченим (або оплата відкочується), CRM стукає в Inbox:

```http
POST <INBOX_WEBHOOK_URL>
X-Crm-Signature: <hmac_sha256(тіло, INBOX_WEBHOOK_SECRET)>
```

```json
{
  "event": "order.payment_received",
  "event_id": "evt_01K2…",
  "occurred_at": "2026-08-13T14:31:00+03:00",
  "data": {
    "order_id": 1499, "order_number": "1499", "client_id": 845,
    "payment_status": "paid", "is_paid": true, "amount": 5650
  }
}
```

Події: `order.payment_received`, `order.payment_reverted` (повернення або зміна
суми). Друга в початковому ТЗ не описана, але без неї Inbox застрягне на
«Оплачено» після повернення.

Підпис рахується по **сирому тілу запиту**, до розбору JSON — тіло кодується
один раз і летить рівно тим рядком, який підписано.

Адреса приймальної сторони: `https://inbox.new.hor-hosting.top/api/crm/webhook`.

П'ять спроб із паузами 10с → 1хв → 5хв → 15хв. Приймальна сторона має
відповідати `2xx` і дедуплікувати за `event_id`.

Летять лише замовлення з `source = telegram_inbox` — інакше нічний перерахунок
балансів вистрелив би пачкою подій по всій історії.

Увімкнено 2026-08-14: `INBOX_WEBHOOK_URL` і `INBOX_WEBHOOK_SECRET` задані на
проді. Поки на боці Inbox секрет не налаштований, вона відповідає `503`, і CRM
просто повторює спроби за розкладом.

## Що НЕ входить

- **Telegram у CRM не підключається.** Канал веде Inbox. У бота може бути лише
  один webhook, тому це взаємне виключення; у CRM стоїть запобіжник
  (`INBOX_TELEGRAM_OWNER`, за замовчуванням `inbox`).
- **Розпізнавання переписки через ШІ** — скасовано за рішенням від 2026-08-13.
- **Промокоди** — у CRM не існують. Є разова знижка на замовлення.
- **Вартість доставки** — у суму замовлення не входить.

## Що заповнити в CRM перед бойовим стартом

| Крок | Де |
|---|---|
| Реквізити брендів (отримувач + IBAN обов'язкові) | Система → Проєкти → Реквізити для рахунків |
| Мінімум днів у тарифах | Довідник → Тарифи → Мінімум днів |
