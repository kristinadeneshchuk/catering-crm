# БУР — прокат будівельного інструменту

Натяжка дизайн-хендофа `design_handoff_bur_rental` на Laravel. Макети з папки
`design/` були прототипами в HTML; тут вони відтворені як застосунок:
Blade + Tailwind v4 + Alpine, дані — в Eloquent, а не в інлайн-масивах.

## Запуск

```bash
composer install
npm install

cp .env.example .env
php artisan key:generate

touch database/database.sqlite
php artisan migrate:fresh --seed     # сид кладе реальний контент з макетів

npm run build     # або npm run dev
php artisan serve
```

Тести: `php artisan test`. Стиль: `./vendor/bin/pint`.

Адмінка — `/admin`. Сид створює два акаунти:

| Пошта | Пароль | Роль |
| --- | --- | --- |
| `admin@bur.local` | `password` | адмін |
| `manager@bur.local` | `password` | менеджер філії «Позняки» |

**Паролі демонстраційні — перед деплоєм змініть їх і не заливайте `StaffSeeder`
на бойовий сервер як є.**

## Адмінка

Filament 5 на `/admin`, українською, в кольорах сайту. Розділи меню:

| Розділ | Що там |
| --- | --- |
| **Замовлення** | Бронювання (з життєвим циклом), Заявки з форм сайту |
| **Каталог** | Товари, Категорії, Бренди, Витратники, Комплекти |
| **Наявність** | Календар зайнятості парку |
| **Географія** | Міста, Філії, Райони, Зони доставки |
| **Контент** | Відгуки, FAQ |

**Інфопанель** відповідає на питання «що робити зараз»: скільки видати й прийняти
сьогодні, що прострочено, скільки броней і заявок необроблено, який відсоток парку
зайнято. Нижче — таблиця сьогоднішніх справ, де видати й прийняти техніку можна
прямо звідти, і виручка за два тижні (без застави — це не дохід).

**Життєвий цикл броні** живе в `App\Services\BookingWorkflow`, а не в кнопках:
нова → підтверджена → видана → закрита (або скасована). Головне правило — зайняті
дати з'являються і зникають разом зі станом броні:

- **Приймання** питає фактичну дату повернення. Здали раніше — перераховуємо за
  фактичним строком і звільняємо невикористані дні. Привезли пізніше — добираємо
  прострочені доби за базовим тарифом, бо знижка за строк на прострочення не діє.
- **Скасування** повертає всі дати в календар: скасована бронь не має тримати
  техніку, яка стоїть на полиці.

**Календар зайнятості** — рядок на модель, стовпчик на день, як у зошиті
менеджера. Клік по вільному дню блокує його на сервіс, клік по сервісному —
знімає. Дні під реальною орендою звідти не звільняються: інструмент фізично в
руках у клієнта, і відпустити його може тільки приймання.

**Ролі.** `admin` бачить усе, `manager` — те саме, але призначений філії
(`users.branch_id`). Звільненому достатньо зняти `is_active`: пароль при ньому
лишиться, а панель більше не пустить.

**Чого в адмінці свідомо немає:** створення броні руками. Бронь, заведена в
обхід сайту, не проходить перевірку наявності — телефонне замовлення менеджер
оформлює через сайт від імені клієнта.

## Наповнення і ринок

Каталог заповнений під київський ринок прокату 2026 року, а не вигаданими
цифрами. Орієнтири, за якими виставлені тарифи (дані з відкритих прайсів
конкурентів — budprokat, samrent, rentnow, pikkampani, rental-power, novarent):

| Позиція | Ринок, ₴/добу | Базовий тариф у нас |
| --- | --- | --- |
| Дрібний ручний інструмент | від 60 | 60–150 |
| Перфоратор SDS-plus | 135–300 | 230–300 |
| Штроборіз | 350–500 | 450 |
| Глибинний вібратор | від 135 | 200 |
| Осушувач повітря | 150–180 | 260 (20 л/добу) |
| Віброплита 90 кг | ~350 | 350 |
| Інверторний генератор 2 кВт | від 315 | 450 |
| Алмазне буріння | від 700 | 850 |

Що з ринку враховано в моделі:

- **Мінімальний строк — 1 доба**, як у всіх. Знижка за строк у конкурентів
  зазвичай «10% від тижня, до 40% за місяць» і згадується текстом; ми
  показуємо її одразу цінами в тарифній сходинці (−17% / −31%).
- **Застава** — за класом техніки, як прийнято в ніші: 400–2 000 ₴ за ручний
  електроінструмент, 2 000–4 000 за бензо- і садову, 4 000–8 000 за віброплити,
  генератори й алмазне буріння.
- **Витратники не входять в оренду.** Бури, диски, коронки, ліска, електроди —
  окремі позиції, які докуповують на видачі. Це стандарт ринку і водночас
  найчастіше джерело непорозумінь, тому написано на кожній картці.
- **Важка техніка від 200 кг самовивозом не видається** — тільки доставка
  гідробортом. Доплати за гідроборт і вагу фіксовані.

Каталог: 48 позицій, 12 категорій, 12 підкатегорій, 21 бренд, 18 витратників,
8 комплектів під задачу, 54 питання в FAQ. Кількість позицій у меню
рахується з бази (`CatalogSeeder::recountCategories`), а не проставляється
руками — цифра в каталозі завжди збігається з тим, що людина побачить
усередині.

## Імпорт чужого каталогу (budprokat)

Прямі запити до сайтів конкурентів із пісочниць CI/агентів зазвичай зарізані
на проксі, тому парсер зроблено командою, яку запускають з машини з нормальним
доступом:

```bash
php artisan scrape:budprokat                       # → storage/app/import/budprokat.json
php artisan catalog:import import/budprokat.json   # → чернетки в адмінці
```

Правила імпорту:

- **Усе приходить неопублікованим.** Чужий прайс — чернетка: менеджер в адмінці
  (Товари → фільтр «Чернетки з імпорту») звіряє ціну, категорію й заставу
  і публікує кнопкою. Вітрина тримається на глобальному scope `published`.
- **Повторний запуск оновлює, а не дублює** — записи зшиваються за `source_url`.
- **Бренд** розпізнається з назви товару; невпізнане падає в «Інші».
- Парсер (`App\Services\Import\BudprokatParser`) — чисті функції під тестами
  на фікстурах. Чужа верстка може змінитися: тоді `scrape:budprokat --dump`
  збереже сирий HTML у `storage/app/import/html`, і селектори правляться
  в одному класі.
- `--delay` між запитами за замовчуванням 400 мс — ми гість на чужому сервері.

Юридична примітка: спарсені описи й тексти — чужий контент. Використовуйте
імпорт для звірки асортименту й цін, а тексти перед публікацією переписуйте.

## Сповіщення менеджеру (Telegram)

Нова бронь і кожна заявка з форм прилітають менеджеру в Telegram: номер,
клієнт з телефоном, склад, дати, сума з окремо виділеною заставою і посилання
в адмінку. Налаштування — два рядки в `.env`:

```
TELEGRAM_BOT_TOKEN=   # токен від @BotFather
TELEGRAM_MANAGER_CHAT_ID=   # chat_id менеджера або групи філії
```

Відправка йде через чергу (`NotifyManagerInTelegram`, 3 спроби): недоступний
Telegram не ламає бронювання. Без токена сервіс просто мовчить — сайт
повноцінно працює і без бота.

## Рішення, які варто знати

**Токени, а не хардкод.** Уся палітра, типографічна шкала, радіуси й брейкпойнти
живуть у `@theme` в `resources/css/app.css`. У розмітці hex-значень немає —
якщо додаєте колір, спершу токен.

**Три радіуси.** `2px` чипси · `6px` кнопки і поля · `12px` картки. `32px` —
тільки pill нижньої навігації. Четвертого радіуса бути не має.

**Тіней немає.** Рівні поверхонь передаються бордером і фоном. Єдиний виняток —
`--shadow-float` для плаваючих шарів: модалка, тост, sticky-панель, bottom nav.

**Дати зберігаються як `Y-m-d`.** `UnavailableDate` має мутатор, який зрізає час.
Без нього Eloquent клав «2026-08-14 00:00:00», `firstOrCreate` не знаходив наявний
рядок, вставляв дубль і падав на унікальному індексі — бронювання на дату, вже
чимось зайняту, віддавало 500. Є тест.

**Наявність — правда, і рахується поштучно.** `unavailable_dates` тримає
зайняті екземпляри по парі товар+філія з посиланням на бронь, `inventory.qty` —
скільки одиниць стоїть на складі. Модель стає недоступною, тільки коли зайнято
всі екземпляри: три перфоратори на Позняках витримують три паралельні броні.
Прив'язка рядка до `booking_id` принципова — без неї дострокова здача однієї
броні знімала б блокування чужої на ті самі дати. Уся логіка в
`App\Services\Availability`, кешувати її агресивно не можна: це головна
перевага сервісу, і вона мусить бути правдивою.

**Ціни рахує сервер.** `App\Services\RentalPricing` бере тариф із бази за
фактичним строком. Ціна, надіслана браузером, ігнорується повністю — тарифну
сходинку в devtools правити легше, ніж здається. Є тест саме на це.

**Тарифна сходинка.** Три рівні на товар у `tariff_tiers`: 1–2 дні базовий,
від 3 днів −17%, від 7 днів −31%. Повзунок днів на PDP одночасно перемикає
активний рівень, зсуває кінцеву дату в календарі та перераховує підсумок —
без кнопки «Розрахувати».

**Місто — наскрізний контекст.** `ResolveCity` резолвить його один раз на запит
із маршруту або сесії й кладе в атрибути. Від нього залежать телефон у хедері,
список філій і зони доставки на всіх сторінках.

**Стан клієнта.** Місто, філія, дати, кошик і список порівняння лежать у
localStorage (`resources/js/stores/booking.js`) і переживають перезавантаження.
Дати з URL мають пріоритет над збереженими — це шаринг посилання.

**Кожна дія — реальний маршрут.** `href="#"` у розмітці немає: кнопка
«Забронювати» в картці лістингу веде на PDP з уже підставленими датами й філією.

## Чого свідомо немає

- **Фото і карти** — плейсхолдери `<x-image-slot>` із зарезервованим
  `aspect-ratio`. Пропорції збережені, щоб при підстановці реальних фото
  сторінка не стрибнула (вимога нульового CLS). Карти — заглушки такої ж висоти.
- **RU-версія** — перемикач у футері передбачений дизайном, але другої мови
  ще немає, тому він неактивний, а не веде в нікуди.
- **SMS** — вхід у кабінет уже працює, але код іде в лог: шлюзу немає.
  Див. розділ «Кабінет клієнта і обране».
- **Оплата** — спосіб оплати зберігається в брони, платіжний шлюз не
  підключений.

## Пошук

Без пошукового движка: сайт живе на шаред-хостингу без SSH, демон Meilisearch
туди не поставити. Тому вся робота винесена в підготовку даних і в розбір
запиту — `App\Services\Search`.

`products.search_text` збирається при кожному збереженні товару і містить назву,
артикул, бренд, категорію та їхню транслітерацію. Опис навмисно не входить: у
ньому «надійний», «зручний» і «професійний», через які будь-який запит знаходить
пів каталогу. Після імпорту або перейменування бренду — `php artisan search:reindex`.

Запит перед порівнянням розкладається на варіанти написання (`SearchTerms`):

| Що вводять | Що з цим робиться |
| --- | --- |
| `gthajhfnjh` | забули перемкнути розкладку → `перфоратор` |
| `бош`, `макіта` | кирилична вимова бренду → `bosch`, `makita` |
| `perforator` | транслітерація в обидва боки |
| `шуруповерт`, `бетономешалка`, `лестница` | розмовні й російські назви → каталожні |
| `hr-2470` / `hr2470` | дефіси в артикулах ставлять як заманеться |
| `перфаратор` | одруківка: Levenshtein по каталогу, коли точних збігів нема |

Слова запиту поєднуються через **І**, а не **АБО**: «бош перфоратор» — це
перфоратори Bosch, а не все Bosch плюс усі перфоратори. Збіг у назві піднімається
над збігом у категорії, далі сортує популярність.

Виправлення одруківки видача показує чесно — «точних збігів немає, показуємо
найближче». Мовчки підмінити запит означало б, що клієнт вирішить, ніби ми його
не зрозуміли.

Списки брендів і синонімів у `SearchTerms` — рукописні й такими мають лишатися:
«болгарка» і «кутова шліфмашина» не мають спільних літер, алгоритм їх не
зв'яже. Поповнюйте зі звітів по порожніх запитах.

Коли з'явиться свій сервер — підключати Scout з Meilisearch треба саме в
`ProductSearch`, решта коду про пошук не знає.

## Тексти

Контент лежить у `database/seeders/data/` окремо від коду: категорії,
підкатегорії, товари, комплекти, FAQ. Редагувати можна і там, і в адмінці —
сиди задають стартовий стан.

Один принцип, від якого написано все: **писати те, чого немає в конкурентів**.
У них — характеристики з коробки виробника, однакові на всіх сайтах ніші. Тут:

- скільки це коштує на конкретну задачу, а не «від»;
- що **не** входить (бури, диски, мішки, пальне) — щоб не з'ясовувати на видачі;
- скільки їсть електрики і чи потягне лінія на об'єкті — через 380 В на
  тепловій гарматі зривається половина оренд;
- чи влізе в легковик;
- **коли цю позицію брати не треба.** Клієнт, якому чесно сказали «вам
  вистачить дешевшого», повертається; клієнт, якому впарили бетонолом під
  плитку, пише відгук.

Сторінки районів пишуться по тому ж лекалу, але з локальною конкретикою: яка
філія ближча, скільки їхати, який житловий фонд. Дванадцять сторінок, де
міняється одна назва, — це doorway, за який знімають з видачі весь набір.

## SEO

Що віддається роботу і чому саме так.

**Індексується каталог, не службові сторінки.** Список закритих маршрутів —
у `layouts/app.blade.php` одним місцем: пошук, обране, кошик, кабінет. Сторінка
пошуку без `noindex` плодить нескінченні тонкі сторінки під кожен запит, і саме
так сайт заробляє репутацію неякісного. `robots.txt` тут не допомагає: заборона
обходу не прибирає сторінку з видачі, вона лише не дає роботу її прочитати.

**Відгуки й рейтинги — тільки справжні.** Сиди позначають свої відгуки
`demo = true`, і глобальний scope їх ховає; рейтинги в сидах обнулені. Зірка на
картці товару з'являється разом із першим реальним відгуком і рахується по
ньому. Константи «4.8» у верстці більше немає — вона там і не мала бути.

**`php artisan check:launch`** — передстартова перевірка: debug, APP_URL,
noindex, демо-контакти, демо-відгуки, залишений `setup.php`, словниковий пароль
адмінки, канали сповіщень. Ненульовий код виходу означає «не запускати».

**Мікророзмітка** — `Organization` і `WebSite` з `SearchAction` на кожній
сторінці, `BreadcrumbList` і `FAQPage` де вони є, `ItemList` на лістингах,
`LocalBusiness` на філіях (адреса, години, телефон міста, координати),
`Product` з `Offer` на картці товару.

Два рішення в картці товару варті окремої згадки:

- `availability` береться з реального календаря, а не з константи. Жива
  наявність — головна відмінність від конкурентів, безглуздо ховати її від
  пошуку; писати `InStock`, коли весь парк в оренді, ще й неправда.
- `businessFunction: LeaseOut` — це оренда, а не продаж. Без цього Google читає
  ціну як вартість покупки перфоратора.
- `aggregateRating` віддається **тільки** якщо в товару є справжні опубліковані
  відгуки, і рахується по них. Поля `rating` / `reviews_count` заповнюються
  руками і в сидах демонстраційні; розмітити їх — це порушення правил Google з
  ризиком ручних санкцій на весь домен.

**Прев'ю посилань.** Open Graph і Twitter Card заповнюються з `title` і
`description` сторінки. В Україні контакт підрядника передають у месенджерах,
тому голе посилання коштує кліків. `og:image` з'явиться разом із реальними фото.

**Рекламні мітки доїжджають до заявки.** `RememberCampaign` знімає `utm_*`,
`gclid` і `fbclid` при першому переході й тримає в сесії до кінця візиту:
клієнт приходить з оголошення, ходить по сайту і лишає заявку через десять
хвилин, коли мітки в адресі вже немає. В адмінці менеджер бачить не просто
«передзвоніть мені», а `google / cpc / perforator-kyiv`. Мітка береться з сесії,
а не з форми — у формі її може підмінити хто завгодно.

**Іконки** — `favicon.svg` і `apple-touch-icon.png` намальовані як заглушки
брендовим кольором, замінити на логотип від замовника.

## Кабінет клієнта і обране

**Вхід — телефон плюс одноразовий код.** Пароля немає навмисно: на сайті оренди
його заводять раз і забувають до наступного разу, а телефон клієнт і так диктує
менеджеру. Два кроки: номер → код → кабінет.

Клієнти живуть у таблиці `clients` і ходять через guard `client`. Це не та сама
таблиця, що `users`: там персонал із доступом до Filament, і зводити їх в одну
«з роллю» не можна — одна помилка в ролі відкриє клієнту адмінку.

**SMS-шлюзу поки немає.** Код іде в `LogSms` — тобто в лог, із рівнем `warning`,
щоб про це не забули. Коли з'явиться оператор, пишеться один клас на інтерфейс
`App\Services\Messaging\Sms` і міняється рядок у `config/clients.php`; решта коду
про канал не знає. Через цей самий канал ідуть і нагадування про повернення. На тестовому майданчику код можна показувати прямо на сторінці:
`CLIENT_SHOW_CODE=true` — але тільки разом із `SITE_NOINDEX=true`, умова подвійна
свідомо.

Що зроблено проти перебору: код лежить у базі хешем, живе 10 хвилин, має рівно
три спроби, а видача нового гасить попередній — стара SMS, знайдена через
тиждень, кабінет не відкриє. Ліміти на форму рахуються і по IP, і по номеру.

**Історія замовлень знаходиться сама.** Клієнт майже завжди спершу бронює і лише
потім заходить, тому при першому вході броні з тим самим номером підбираються за
`client_id`. Тримається це на канонічному телефоні (`App\Support\Phone`):
«0672458080» і «+380 67 245 80 80» — той самий кабінет.

**Менеджер бачить клієнтів окремим розділом** (Замовлення → Клієнти): скільки
оренд, скільки зараз на руках, скільки приніс і коли востаннє брав. Виручка
рахується тільки по закритих бронях — підтверджена й видана ще можуть
скасуватися, а застава не рахується взагалі, бо повертається. Кнопки «створити»
там немає: клієнт заводиться сам при першому вході. Є дія «підтягнути броні» —
на випадок, коли менеджер виправив одруківку в телефоні й броні треба
перепідв'язати.

**Обране працює без входу.** Список гостя живе в localStorage поруч із кошиком:
вимагати реєстрацію заради закладки — найшвидший спосіб втратити і закладку, і
клієнта. Після входу гостьовий список **зливається** з серверним, а не заміщує
його: людина додавала обране і з телефона, і з ноутбука.

Сторінка обраного для гостя добирає картки окремим запитом за id
(`/favourites/items`). Віддати весь каталог і сховати зайве було б простіше, але
цей трафік росте разом із каталогом.

## Знижки постійним клієнтам

Сходинка за кількістю **завершених** оренд, цифри в `config/loyalty.php`:

| Завершених оренд | Знижка | Рівень |
| --- | --- | --- |
| 3 | −3% | Постійний |
| 6 | −5% | Свій |
| 12 | −7% | Бригада |

Числа свідомо скромні: на товарі вже стоїть тарифна сходинка (−17% від 3 днів,
−31% від 7), і знижка постійного накладається зверху на неї. Десять відсотків
лояльності поверх тридцяти одного — це вже робота в нуль. Стеля (`max_percent`)
захищає і від ручної знижки: «домовився з бригадиром» не має перетворюватись
на мінус тридцять.

Рішення, які варто знати:

- **Рахуються тільки закриті броні.** Підтверджена й видана ще можуть
  скасуватися; обіцяти знижку за замовлення, яке не відбулося, означає потім
  її забирати.
- **Знижка діє тільки на оренду.** Витратники йдуть з мінімальною націнкою,
  доставка — це гроші перевізнику, застава взагалі не дохід.
- **Клієнт шукається за телефоном, а не за сесією.** Постійний клієнт
  заслуговує на свої відсотки й тоді, коли забув увійти в кабінет.
- **Відсоток фіксується в броні.** При прийманні техніки перераховується сума
  (строк міг змінитися), але не відсоток: клієнт бачив його при оформленні.
- **`rent_total` лишається повною сумою.** Знижка стоїть окремим рядком і в
  броні, і в чеку — видно, скільки клієнт зекономив і скільки ми віддали.

Менеджер може поставити персональну знижку в картці клієнта: вона перебиває
сходинку (але не стелю), і в списку клієнтів позначена як «ручна».

Кабінет показує рівень і скільки оренд лишилось до наступного — без цього блок
був би просто похвалою, а він має давати причину повернутися.

## Нагадування за добу до повернення

`php artisan reminders:returns`, у розкладі — щодня о 18:00. Час обраний свідомо:
раніше клієнт ще на об'єкті й забуде, пізніше — вже не встигне перепланувати
завтрашній день.

Навіщо: найдорожча претензія в оренді — «мене не попередили». Клієнт забув дату,
приїхав на день пізніше, отримав рахунок за прострочення **за базовим тарифом**
(знижка за строк на прострочення не діє) і пішов писати відгук. SMS напередодні
знімає і претензію, і половину прострочень — техніка повертається вчасно й
одразу їде наступному клієнту.

Що враховано:

- **Один раз на бронь.** Відмітка `bookings.return_reminded_at` ставиться одразу
  після відправки. Крон, який спрацював двічі, другої SMS не пришле — це наші
  гроші і вигляд несправного сайту.
- **Тільки підтверджені й видані.** За нову бронь, яку клієнт не забрав,
  нагадувати про повернення безглуздо; за закриту — тим паче.
- **Одна SMS.** 160 символів — межа, далі оператор рахує як дві. Якщо довга
  назва моделі не влазить, у тексті лишається кількість позицій: номер броні
  клієнт однаково знайде в кабінеті.
- **Менеджеру — список.** Тим же прогоном у Telegram іде перелік завтрашніх
  повернень: кого чекати і кому дзвонити, якщо не приїхали.

`--dry` показує, кому пішло б, і не надсилає нічого.

Планувальник на хостингу заводиться одним крон-рядком:

```
* * * * * cd ~/bur_app && php artisan schedule:run >> /dev/null 2>&1
```

## Шрифти

Oswald (дисплей), Golos Text (текст), JetBrains Mono (числа) — свої, лежать у
`resources/fonts/`, підключені через `@font-face` на початку `resources/css/app.css`.
Vite їх хешує і кладе в `public/build/assets/`.

Чому не CDN: шрифти в критичному шляху LCP, а сторонній домен — це зайвий DNS +
TLS-handshake перед першим байтом. На мобільному 3G це половина секунди порожнього
тексту. Плюс сайт більше не залежить від доступності чужого CDN.

Дев'ять файлів, 188 КБ разом: три родини × три підмножини. Усі три родини
варіативні, тому один файл покриває весь діапазон ваг (`font-weight: 400 600`) —
окремі файли на кожну вагу не потрібні.

Підмножини й навіщо кожна:

| Підмножина | Навіщо |
| --- | --- |
| `cyrillic` | основний текст; і, ї, є, ґ саме тут |
| `cyrillic-ext` | заради **₴** (U+20B4) — без неї гривня падає в системний шрифт і стоїть чужою поруч із ціною |
| `latin` | назви брендів (Bosch, Makita), лапки, тире, апостроф |

Грецька та в'єтнамська підмножини свідомо не тягнуться.

Preload у layout — тільки на `golos-text-cyrillic.woff2`: ним набрано майже все
на першому екрані. Решту браузер витягне сам за `unicode-range`; вантажити їх
наперед означало б відбирати смугу в того єдиного файлу, від якого залежить LCP.

Оновити шрифти:

```bash
curl -H 'User-Agent: Mozilla/5.0 Chrome/120' \
  'https://fonts.googleapis.com/css2?family=Golos+Text:wght@400..600&family=JetBrains+Mono:wght@400..700&family=Oswald:wght@500..700&display=swap'
```

— у відповіді лежать посилання на `.woff2` по підмножинах. Завантажити потрібні
три (`cyrillic-ext`, `cyrillic`, `latin`), покласти в `resources/fonts/` під тими ж
іменами, `unicode-range` у `app.css` звірити з відповіддю: Google їх час від часу
переглядає.
